# DR0005: Documented exception may escape

## Summary

An XML-documented, non-allowed exception may escape a function returning `Result<TValue, TError>`, `Task<Result<TValue, TError>>`, or `ValueTask<Result<TValue, TError>>`.

## Details

This rule reports exceptions declared by XML documentation on:

- Invoked methods
- Object constructors
- Property accessors
- User-defined operators and conversions

Explicit `throw` statements and expressions are analyzed separately by [DR0004](DR0004.md).

When `Darp.Results` is consumed as a NuGet package, its build-transitive target supplies XML documentation files shipped beside resolved references to the analyzer. Documented exceptions therefore flow across package boundaries when the referenced package includes its XML documentation file.

An exception is not reported when it is caught by a compatible catch clause before it leaves the Result-returning function. Unfiltered catches, compile-time `true` filters, and catch-variable type patterns that are guaranteed to match the known exception type are recognized. For example, `when (exception is IOException or UnauthorizedAccessException)` handles either documented type. Other runtime-dependent filters are treated conservatively because they can reject the exception.

For a method returning `Task` or `ValueTask`, the catch clause must surround the directly awaited call. Calls followed by `ConfigureAwait` are also recognized. The analyzer does not track a task stored in a variable to a later `await`, so such calls are reported conservatively.

XML documentation describes the complete API contract, but its exception conditions are not machine-readable. Use `excluded_members` when a member's documented conditions cannot apply or should not be treated as Result failures in your project.

## Default allowed exceptions

The following exception types and their derived types are allowed by default:

- `System.ArgumentException`
- `System.OperationCanceledException`
- `System.NotImplementedException`
- `System.NotSupportedException`
- `System.Diagnostics.UnreachableException`
- `System.ObjectDisposedException`
- `System.Runtime.CompilerServices.SwitchExpressionException`
- `System.Threading.SemaphoreFullException`

## Examples

### Noncompliant

```csharp
Result<string, ReadError> Read(string path)
{
    return File.ReadAllText(path);
    // IOException and UnauthorizedAccessException are documented by File.ReadAllText.
}
```

### Compliant: return the failure

```csharp
Result<string, ReadError> Read(string path)
{
    try
    {
        return File.ReadAllText(path);
    }
    catch (IOException exception)
    {
        return ReadError.From(exception);
    }
}
```

### Compliant: declare the exception contract

An XML exception declaration permits the exception within the calling function. Result-returning callers that invoke the function are still warned unless they catch, declare, allow, or exclude the exception contract.

```csharp
/// <exception cref="IOException">The file could not be read.</exception>
Result<string, ReadError> Read(string path)
{
    return File.ReadAllText(path);
}
```

## Code fix

For an editable named method or property, **Document escaping exceptions** adds empty XML exception elements to the declaration. Use this only when the exception genuinely belongs to the member's public contract.

## Configuration

### Severity

DR0005 is a warning by default. Configure its severity independently from DR0004:

```ini
dotnet_diagnostic.DR0005.severity = warning
```

### Excluded members

Set a pipe-separated list of XML documentation member IDs. Excluding a member also excludes exception contracts inherited from that member through an override or interface implementation. The pipe follows the .NET analyzer convention for symbol lists and does not conflict with commas inside method documentation IDs.

```ini
dotnet_code_quality.DR0005.excluded_members = P:System.Array.Length|M:System.IO.File.ReadAllText(System.String)
```

Documentation IDs use `P:` for properties, `M:` for methods and constructors, and the standard XML documentation syntax for parameters and generic types.

### Allowed exception types

Set one shared, pipe-separated list of fully qualified exception type names for DR0004 and DR0005:

```ini
dotnet_code_quality.darp_results_allowed_exception_types = System.ArgumentException|System.OperationCanceledException|System.NotImplementedException|System.NotSupportedException|System.Diagnostics.UnreachableException|System.ObjectDisposedException|System.Runtime.CompilerServices.SwitchExpressionException|System.Threading.SemaphoreFullException|MyCompany.ExpectedException
```

When configured, this option replaces the default list for both rules. Configuring `System.Exception` allows every explicit and XML-documented exception.

Normal Roslyn suppressions such as `#pragma warning disable DR0005`, `SuppressMessageAttribute`, and `NoWarn` are also supported.
