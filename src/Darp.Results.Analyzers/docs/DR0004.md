# DR0004: Explicit exception may escape

## Summary

An explicitly thrown, non-allowed exception should not escape a function returning `Result<TValue, TError>`, `Task<Result<TValue, TError>>`, or `ValueTask<Result<TValue, TError>>`.

## Details

Expected failures should be returned through the Result error channel. This rule reports explicit `throw` statements and expressions in Result-returning functions.

The rule does not report exceptions documented by invoked members. Those contracts are analyzed separately by [DR0005](DR0005.md).

An exception is not reported when it is caught by a compatible catch clause before it leaves the Result-returning function. Unfiltered catches, compile-time `true` filters, and catch-variable type patterns that are guaranteed to match the known exception type are recognized. For example, `when (exception is IOException or UnauthorizedAccessException)` handles either known type. Other runtime-dependent filters are treated conservatively because they can reject the exception.

## Default allowed exceptions

The following exception types and their derived types are allowed by default:

- `System.ArgumentException`
- `System.OperationCanceledException`
- `System.NotImplementedException`
- `System.NotSupportedException`
- `System.Diagnostics.UnreachableException`
- `System.ObjectDisposedException`
- `System.Runtime.CompilerServices.SwitchExpressionException`
- `System.Threading.SemaphoreFullException`

## Examples

### Noncompliant

```csharp
Result<int, Error> Calculate()
{
    throw new InvalidOperationException();
}
```

### Compliant: return the failure

```csharp
Result<int, Error> Calculate()
{
    return Error.InvalidState;
}
```

### Compliant: declare the exception contract

An XML exception declaration permits the exception within that function. Result-returning callers are analyzed by DR0005 when they invoke the function.

```csharp
/// <exception cref="InvalidOperationException">The calculator is not initialized.</exception>
Result<int, Error> Calculate()
{
    throw new InvalidOperationException();
}
```

Documenting a base exception type permits derived exception types. Documenting `System.Exception` permits all exceptions for that function.

## Code fix

For an editable named method or property, **Document escaping exceptions** adds empty XML exception elements to the declaration. No fix is offered for lambdas or local functions because they cannot expose an XML documentation contract.

## Configuration

### Test projects

DR0004 and DR0005 are disabled by default when the MSBuild property `IsTestProject` is `true`. Enable them in a test project with:

```xml
<PropertyGroup>
  <DarpResultsAnalyzeTestProjects>true</DarpResultsAnalyzeTestProjects>
</PropertyGroup>
```

### Severity

Disable the rule globally or for an `.editorconfig` section with:

```ini
dotnet_diagnostic.DR0004.severity = none
```

### Allowed exception types

Set one shared, pipe-separated list of fully qualified exception type names for DR0004 and DR0005:

```ini
dotnet_code_quality.darp_results_allowed_exception_types = System.ArgumentException|System.OperationCanceledException|System.NotImplementedException|System.NotSupportedException|System.Diagnostics.UnreachableException|System.ObjectDisposedException|System.Runtime.CompilerServices.SwitchExpressionException|System.Threading.SemaphoreFullException|MyCompany.ExpectedException
```

When configured, this option replaces the default list for both rules. Configuring `System.Exception` allows every exception.

Normal Roslyn suppressions such as `#pragma warning disable DR0004`, `SuppressMessageAttribute`, and `NoWarn` are also supported.
